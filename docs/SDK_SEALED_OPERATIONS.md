# Sealed SDK operations

The optional Rust `sealed-operations` feature exposes
`expert::replay::{RecoveryKey, SealedOperation}` for a trusted durable protocol.
It closes the SDK interface gap between platform randomness and exact KEM recovery.
It is not enabled by default, has no new C/JNI exports, and retains ABI major **2**.

## Authority and order

`RecoveryKey::from_host_key` derives a separate wrapping key with HKDF-SHA256 from
a protected, CSPRNG-generated 256-bit host key. The host supplies a wrapping key,
not KEM coins. Its quality and secure storage are host responsibilities; a host
controlling this key can forge local records. Protect it separately from database
backups. The derived owner has no export or clone and erases its allocation on close
or drop; this does not erase host key copies, backups or OS/provider temporaries.

`reserve_key` and `reserve_encapsulation` draw their private coins from the platform
CSPRNG. All failures are returned without a fallback. The service must atomically
persist the sealed record with its complete operation intent, claims and writer
fence **before** invoking `generate_key` or `encapsulate`. Unknown reservation or
result commits require exact journal reconciliation. Never turn a missing/corrupt
record into a new reservation under the same operation ID.

The SDK cannot enforce this storage ordering on a caller. It also cannot detect a
replayed old database, enforce one-time consumption, authenticate remote peers or
provide protocol freshness. These remain the durable protocol's responsibilities.
The operation ID is nonzero public correlation data; it is not an authorization,
randomness source or proof that a reservation committed.

## Exact input binding

The record binds the complete 68-byte SDK policy identity (pinned root digest,
version and policy digest), operation ID, a closed operation kind and input digest.
Key generation takes no variable cryptographic inputs. Encapsulation binds both
public-key components and the full application context with its length. A token
cannot switch roles, policies, IDs, recipients or contexts. Reopening under a new
runtime with the **same verified policy** is supported; the generated key/secret
belongs to that runtime and its current lifecycle and quota.

Successful replay uses the unchanged SDK key generation or ContextBound
encapsulation implementation. It draws no replacement KEM coins, and reproduces
the exact private/public key or ciphertext/shared secret. KEM validation,
noncontributory-share rejection, policy denial and admission limits remain active.
Quota failure leaves the sealed record available; the service must preserve its
selected command while waiting rather than substituting another one.

## Encoding v1

All fixed fields are byte arrays; the context length is a big-endian u32.

`QPSOP001[8] || kind:u8 || policy[68] || operation_id[32] || inputs[32] || nonce[24] || ciphertext || tag[16]`

The entire 165-byte header is XChaCha20-Poly1305 associated data. The 24-byte nonce
is freshly generated by the platform CSPRNG on reservation. HKDF uses the default
zero salt and info `Q-PERIAPT-SDK-SEALED-OPERATIONS-KEY/v1` to derive the 32-byte key.

| Kind | Sealed plaintext | Input digest | Total record |
| --- | --- | --- | --- |
| 1: key generation | ML-KEM keygen seed[64], X25519 scalar[32] | zero[32] | 277 bytes |
| 2: encapsulation | ML-KEM coins[32], X25519 scalar[32] | SHA-256(domain, public[1216], context_length[4], context) | 245 bytes |

The encapsulation input domain is `Q-PERIAPT-SDK-SEALED-ENCAPSULATION-INPUT/v1`.
There is no plaintext RNG/coin constructor. `SealedOperation::from_bytes` checks
version, kind and exact length; it does not assert authenticity. Execution verifies
the expected binding and AEAD before consuming any private bytes. Truncation,
extension, mismatch and authentication failure are explicit errors. No automatic
format migration or fresh-generation fallback exists.

## Continuity integration boundary

The Continuity candidate's initiator journal now uses staged reservations: first
a reply-key reservation, then an encapsulation reservation once its exact public
context is known, then a private purpose/body-bound signing reservation. It recovers
the same public outputs when killed after computation but before result pin, and
an independent live responder verifies the recovered handshake. Its responder
`Executing` state still uses the non-repeatable path and remains suspended on restart.
Each stage durably pins its complete intent before execution. Reserving generic
coins and allowing the caller to choose the context afterward would permit reuse
under different commands and is deliberately unsupported.

The signing reservation is private to the candidate's authenticated journal, not
a public SDK primitive. Responder integration, immutable outer write/anchor intents,
prekey-secret inventory and anti-rollback anchors remain required in the full 0.2.0 work.

Tests compare exact recovered private keys and real peer decapsulation, exercise
all-byte corruption and length rejection, input/policy/kind substitution, runtime
revocation, owner recreation/close and key quota exhaustion. Hosted Linux minimum
compiler/current compiler and macOS lanes run the optional feature explicitly.
