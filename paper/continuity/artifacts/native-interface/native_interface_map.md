# Native interface map：opaque renderer v1.2 到固定源码的映射

**固定源码：** `228c944fc476e3e57d6c08063cacb19bca5b360e`。**依据：** `work/theory_increment.md` v1.2，SHA-256 `98e0df8b8536d5d43cd191a0a9851676345e8c20aebe82a298c4d86dd6b8035e`。

## 已成立的对应关系

image/intent 的实际wire布局、六个摘要域、原pending target的保留与安装、精确retry，以及unknown commit后的关闭/reopen路径，均已有逐调用源码对应。opaque renderer的对象身份可以落到fresh sealing invocation与完整intent prefix上；reservation origin则沿原token/record复制保留。cleanup的三个报告族也已按真实返回内容和key位置分开，后序closure/fanout对earlier resolution key/tag的依赖有明确编码链。

本表列出 **37 项映射**，直接引用 **27 个固定源码文件**；其中 **26 项**属于已匹配编码、状态转换、已知输入计算或实际依赖边。其余条目把独立F/report/validation/acquisition接口定位到了具体函数。这里的“已匹配”是所列源事实和typed构造器的对应，不把所有Rust调用方、任意损坏存储或完整网络协议自动纳入有限引理。

本轮从Git对象提取107个相关文件用于稳定检索，每个文件计算Git blob SHA-1与SHA-256；表中仅将实际引用的区域计为审查证据。没有重跑native实验，也没有改repo或主稿。随机nonce/新key采用独立均匀分布是密码学模型前提；源码证据是对应getrandom::fill调用及先后关系。

### 使用方式

下面每条给出native调用、typed接口、直接观察和后续依赖编号。相同后续依赖在末尾统一解释，避免把一个边界在每项成果之后重复扩成整体否定。固定版本的源码链接包含行号；机器可读的对应字段和每个被引用文件的hash在 `map.json`。

## 两个对后续证明立即有用的判断

**正常exact-handle路径可以沿已有原对象目录逐步编译。** `reserve → apply → load/reopen`没有把pending target重新生成；copy和fresh seal的区别也与v1.2的equality lemma一致。因此可以先为这一集合写明确的source-to-handle invariant，而不需要把所有native函数一次塞入同一证明。

**多report证明已经有具体依赖图和实际验证调用点。** earlier resolution key在Traffic编码中，later closure/fanout transcript包含它；正常冻结状态的重放保持原row。multi-report theorem应对应这些MAC/validate/ack调用，同时把Batch-only key fragment和resolution应用明文输出保持为独立接口。仅知道key draw彼此独立不足以处理后序transcript中的earlier key，但源码已给出可用的creation-order结构。
