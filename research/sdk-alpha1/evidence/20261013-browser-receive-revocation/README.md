# Retained browser receive descriptors after peer revocation

Four fresh actual installed browser/native cohorts test the receive half of peer-roster admission on engine revision `e858ec00`. Each establishes an original session, creates a real native ciphertext through the owned SDK, and opens the browser session descriptor before installing the new signed roster. The target either preserves the peer or revokes it with an empty roster. New ciphertext and already consumed duplicates are tested separately.

With membership preserved, new ciphertext invokes the host once and returns an authenticated consumption reply; a duplicate invokes no host callback and returns the exact original ACK. With the peer revoked, both new and duplicate ciphertext return `Scope`, close the owner, execute zero plaintext callbacks and return no reply. The original application effect remains absent for new ciphertext or unchanged for an already consumed duplicate. Fresh session reopening is also refused. Local journal identity and prekey remain unchanged.

The native sender's actual durable status is checked before and after the boundary. An unconsumed revoked message remains `Committed`; it is never reported as acknowledged. Already consumed messages remain `Acknowledged` because their baseline receipt was authenticated before revocation, not because the rejected call produced a new receipt.

The first fixture incorrectly tried to send an already acknowledged outbox again after the positive duplicate test. The SDK correctly returned `Retired`. The corrected fixture compares the returned duplicate ACK against the authenticated baseline and reads the retained sender status. The failed attempt and original driver are retained; no product code or assertion on the receive boundary was weakened.

`CHECKS.json` and `CAPTURE.zip` bind the package, native binaries, fixture code, public inputs and operation results. Full repetitive witness/native raw traces stay task-local with a complete hash manifest. No private signing/wrapping material, journal databases or browser profiles are included. The peer and witness share the Rust implementation and run on loopback. This complements the installed cached-send and reopen revocation tests; it does not establish automatic roster distribution, cross-platform deployment, independent implementation, performance, PCS or release readiness.
