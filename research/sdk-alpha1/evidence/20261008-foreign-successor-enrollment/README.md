# Foreign successor enrollment through existing public APIs

The replacement workload now delegates device-side registration to the selected
C, Swift or Kotlin client. Independent account issuance and witness replacement
commit remain controller responsibilities. No product API, export or protocol
permission was added.

Ten actual successor processes provision the wrapping key, create generation 2,
produce and reopen the original signed request, accept and re-accept the approved
grant, prepare the original genesis, attempt activation before replacement, then
activate and reopen after its independent commit. Every returned signing identity
and accepted journal must match the native public readback. The first activation
must fail with the witness error; a bounded single-exchange carrier checks the
exact successor subject and the real store's Scope rejection, without weakening
the general witness fixture's error handling. Reopening must expose the original
`Activating` journal and, after authorization, its original `Active` journal.

Each run then executes the existing eight foreign retirement processes. Complete
host report bytes and identity, purpose-separated acknowledgement, three exits
without completion, and logical journal/signer erasure remain checked. The public
reader now requires all ten distinct successor process identities before it can
label a run foreign. Missing/reordered stages, reused process IDs and native-only
fallback records fail its negative controls.

All eight combinations passed on macOS arm64: C and Swift Debug/Release, and
Kotlin Debug/Release with Serial/G1. The original native connection workload also
passed, including native generation replacement, retirement, original uncertain
delivery, restart, bidirectional traffic, cancellation, rekey and durable
revocation. Rust 1.90 compilation, Rust 1.98.1 strict Clippy and 24 affected
artifact tests passed. The previously committed Kotlin source `e4d743f2` separately
passed all 2660 artifact tests; that result does not cover this newer change.

Three development failures are retained. The first fixture omitted TLS inputs
before public activation, producing configuration error 500. After supplying those
inputs, the attempted `prepare` after a refused activation correctly failed:
`Activating` must recover the retained genesis. The final fixture obeys that
contract. Strict Clippy subsequently found nine indexing/slicing sites; exact
slice patterns and a fixed-width request buffer resolved them without suppression.
These are test integration corrections, not evidence of a repaired product bug.

`QUALIFICATION.json` and `CAPTURES.zip` bind exact source hashes, commands, actual
consumer/harness/library identities, selected public inputs and records, failures,
and passing outcomes. C/Swift use previously qualified installed consumers;
Kotlin uses the verified private Maven consumer. The new harness is a development
build. It does not constitute complete qualification of newly assembled archives.
Private databases, signer/wrapping keys and TLS private keys are excluded.

Rust CodeQL for `15819e51` completed analysis, quality checks and upload. Its
476,946,944-byte diagnostic artifact is retained remotely through 2026-10-15;
metadata and digest are captured, but no fresh SARIF disposition is claimed.

Successor prekeys and fresh-generation TLS remain native Rust in this workload.
