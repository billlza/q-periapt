# SDK policy values at reported cryptographic sinks

This checkpoint reviews alerts **700** and **537**, raw Rust SARIF results
**789** and **792** in analysis **1930866657**. That analysis contains 878 results
and used merge commit `760da743a40e1a5876e973308c2341d2b000eeff`.
The current comparison source is `abc731a11e60c91c30bbaa362eb36095c0157c93`.
Both reports are false positives for the named cryptographic sinks. No product
code, query, severity or remote alert state was changed.

| Reported source | Actual value and use | Named sink assessment |
| --- | --- | --- |
| `Runtime::is_enabled`, SDK `lib.rs:315` | A boolean policy-admission result. The policy verifier and operation gate refuse disabled authority; they do not return key bytes. | Both journal cipher constructors borrow the independently supplied `JournalKey`. The reported path crosses containing policy/service/journal owners without an assignment from the boolean to that key. |
| `Runtime::policy_binding`, SDK `lib.rs:303` | A 68-byte buffer whose entire contents are overwritten by the 32-byte root digest and 36-byte trusted policy state. This is public deterministic metadata. | The three bootstrap-prefix calls use a distinct nonce generated by `getrandom` or restored from its authenticated plan. The two journal constructors use the original wrapping key. Policy metadata is neither of those fields. |

The sealed-operation path authenticates the policy binding as header data. It
separately fills operation entropy and a 24-byte AEAD nonce, propagates entropy
errors, and validates the exact header and ciphertext before returning recovered
entropy. Bootstrap plans separately retain their 32-byte nonce. Journal creation
fills all 32 key bytes before publication; reopening/decode reads the exact
retained key payload. These boundaries must remain intact. Randomizing policy
identity, removing enablement checks or replacing a retained nonce on replay
would change the contract rather than repair these reports.

[DISPOSITIONS.json](DISPOSITIONS.json) records the inspected boundaries and
current line anchors. All eight supplied flow threads (292 locations), seven
message-named sink occurrences and six additional related locations are retained.
Seventeen flow/sink files plus two supplementary producer/test files are captured
at both source identities. Nine of the seventeen flow/sink files changed between
commits. Their relevant key/nonce constructors, policy checks and owner transfers
were reread; whole-file equality and review of every change are not claimed.

Five existing tests passed on current macOS arm64 source with
`--features sealed-operations`: exact key recovery with quota enforcement,
input-bound encapsulation replay, tamper/truncation/wrong-key refusal, policy
revocation/owner lifecycle, and entropy-failure nonpublication. The first command
used `--all-features`, inadvertently selecting the Linux-only AVX2 candidate;
the build correctly refused that platform combination before any test ran.
The corrected invocation preserved the platform guard and used a fresh build
output. These finite tests support their named behavior, not whole-program
information-flow or cryptographic proofs.

[CAPTURE.json](CAPTURE.json) binds 70 members, including the full raw SARIF,

[READBACK.json](READBACK.json) verifies those bytes, selected results and test

The first supplementary-source collector named a nonexistent `context.rs` and
stopped; its replacement used the actual `lib.rs`. An initial flow reader
counted auxiliary related locations as message-named sinks; the corrected reader
resolves message location IDs and verifies both sets. Original inputs and failed
recipes remain retained.
